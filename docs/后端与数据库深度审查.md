# 后端与数据库深度审查报告

更新时间：2026-10-26
审查范围：`backend/app`（models / db / routers / services / seed / config）与数据库表结构
审查目标：设计模式可支撑后续开发与修正；数据库有合适的规范与粒度

---

## 一、总体结论

| 维度 | 现状评价 | 风险 |
|------|----------|------|
| 分层结构 | routers / services / models 已分层，但边界泄漏 | 中 |
| 设计模式 | 几乎没有可扩展抽象（无 Repository / Strategy / DI 注入） | 高 |
| 数据库规范 | 缺 FK、缺索引、缺 CHECK、时间字段不规范、迁移机制脆弱 | 高 |
| 数据粒度 | 复盘报告/标签等关键结构被塞进 JSON 或逗号串 | 高 |
| 可测试性 | 仅 smoke_test，服务不可注入、启动有副作用 | 中 |
| 依赖声明 | `cryptography` 被直接 import 但未写入 requirements.txt | 中 |

当前规模下功能可跑，但再加「产品卡入库、维度统计、多级组织、导出报告、知识审核」等需求时，会反复改到同一批巨型文件，回归风险大。

## 二、数据库问题

### 2.1 引用完整性（规范性 — 高优先）

`backend/app/models.py` 中三条逻辑关联没有外键：

| 字段 | 现状 | 应为 |
|------|------|------|
| `KnowledgeItem.document_id` | 裸 `Integer` | `ForeignKey("knowledge_documents.id")` |
| `KnowledgeItem.document_version_id` | 裸 `Integer` | `ForeignKey("knowledge_document_versions.id")` |
| `KnowledgeDocument.current_version_id` | 裸 `Integer` | `ForeignKey("knowledge_document_versions.id")`（注意循环依赖，可延迟约束） |

后果：删文档时靠路由手动级联删除（`knowledge.py:402-404`），漏一处就产生孤儿行；`current_version_id` 可指向不存在的版本。

### 2.2 索引缺失（性能 — 高优先）

全库只有 `users.username` 有索引。以下字段在查询/关联路径上，均无索引：

- `training_sessions.owner_id`、`status`、`created_at`
- `training_messages.session_id`（对话拉取必经）
- `knowledge_items.document_id`、`document_version_id`、`status`、`stage`、`scenario`
- `knowledge_documents.status`、`source_type`、`title`
- `knowledge_document_versions.document_id`

`find_relevant_knowledge` 目前是「全量拉 active 行 → Python 打分」（`services/knowledge.py:42-53`），数据量上去后既慢又浪费内存；至少要先把过滤字段索引化，再做 SQL 侧粗筛。

### 2.3 枚举与 CHECK 约束缺失（规范性）

以下字段全是自由字符串，无 `CheckConstraint`/`Enum`，脏数据可直接入库：

- `users.role`（实际只用 `sales`/`admin`）
- `knowledge_documents.status` / `parse_status`
- `knowledge_items.status` / `chunk_type` / `stage` / `scenario`
- `training_sessions.status` / `training_type`
- `training_messages.role`（`sales`/`customer`）/ `speaker`（`buyer`/`tech`/`boss`）

建议：至少给 status / role / speaker / message.role 加 CHECK；业务词表（stage/scenario）先保留字符串但由服务层白名单校验，避免词表变更要改表。

### 2.4 时间字段不规范

- 全部使用 `datetime.utcnow`（Python 3.12 已弃用，且返回 naive UTC）
- 多数表缺 `updated_at`
- 未使用 `DateTime(timezone=True)`

建议统一为 `datetime.now(timezone.utc)` + `DateTime(timezone=True)`，并给可变表补 `updated_at` + `onupdate`。

### 2.5 数据粒度问题（核心）

**（1）`training_reports` 一行塞 6 个 JSON 大字段**

```
scores / good_lines / risk_lines / alternatives / checklist / citations
```

`dashboard.py:28-39` 已经在 Python 里解开 `scores` JSON 做维度平均——这正说明有「按维度聚合」的查询需求，却被 JSON 粒度堵死。后续「弱项趋势、团队对比、导出报告」都要扫全表解 JSON。

建议拆表（保留 JSON 做快照亦可，但统计走子表）：

```
report_scores(report_id, name, value, reason)
report_todos(report_id, title, detail, due, sort_order)
report_citations(report_id, source, reason, sort_order)
```

`good_lines/risk_lines/alternatives` 数量少、展示用，可暂留 JSON。

**（2）`knowledge_documents.tags` 是逗号分隔 `Text`**

违反 1NF，无法按标签过滤/统计。应为 `document_tags(document_id, tag)` 关联表，或至少 `String[]` + GIN 索引。

**（3）`knowledge_items` 复制了文档级属性**

`source_type / recommended / banned / customer_type` 在 document 与 item 冗余；`knowledge.py:320-324` 在文档更新时批量 UPDATE 所有 chunk，就是粒度错位的直接后果。  
建议：item 只保留切片自身字段（content / chunk_type / section / page / confidence / order），文档级属性查询时 JOIN document（或物化视图）。

**（4）`llm_configs` 单行表**

`db.get(LLMConfig, 1)` 硬编码主键 1，语义上是「配置」不是「实体」。建议改为 `app_settings(key, value, updated_at)` 或明确 singleton 约定 + 唯一约束。

**（5）`embedding_json` 预留字段**

类型 `JSON`，与真实向量库（pgvector）不兼容。若后续要语义检索，应单独规划，不要在 JSON 上继续堆。

### 2.6 软删除不一致

- 表里有 `status: active/disabled`
- 但 `DELETE /knowledge/documents/{id}`、`DELETE /training/sessions` 是硬删除

「启停」与「删除」语义并存且行为不一致。建议：管理面统一软删（`status=deleted` + `deleted_at`），硬删仅限管理员清理。

### 2.7 迁移机制脆弱

`db/migrations.py` 的 `ensure_runtime_schema` 只会 `ADD COLUMN`，不能做：

- 改列类型 / 收紧约束
- 加索引、加外键、加 CHECK
- 删列、回滚
- 多环境版本管理

一旦本轮要加 FK/索引/子表，该机制不够用。建议引入 **Alembic**，`create_all` 只留给本地空库首装。

### 2.8 其他

- 全库无 `created_by` / `updated_by` 审计字段
- `training_sessions.template_id` 是 `String`，与前端模板无外键/无约束，模板改名即失效
- `seed.py` 写死默认密码 `123456`，演示可用，正式环境必须替换或禁用

## 三、后端架构 / 设计模式

### 3.1 分层边界泄漏（高优先）

路由层直接操作 ORM：`routers/` 下 `db.query/add/delete/commit` 约 **60+ 处**，其中 `knowledge.py` 把「文档-版本-切片」编排逻辑（`_create_document_version`、`_create_items_from_parsed`、`_deactivate_document_chunks`…）全写在路由模块里。

后果：

- 换存储 / 加缓存 / 加审计日志要改所有路由
- 业务规则无法单测（必须起 FastAPI + DB）
- 同一事务边界散落在 handler 中间，`stream_message` 里甚至另开 `SessionLocal`

建议目标结构：

```
routers/          # 只做：鉴权、参数校验、调 service、映射 schema
services/         # 业务用例 + 事务边界
  training_service.py
  knowledge_service.py
  report_service.py
repositories/     # 持久化查询封装（可先薄层，不必一次到位）
  session_repo.py
  knowledge_repo.py
```

### 3.2 LLMClient 是「上帝类」

`services/llm.py` **1206 行**，混了 5 类职责：

1. 角色标签解析（`extract_speaker` 及 4 个正则）
2. Prompt 构建（客户出题 / 报告 / 建议 / live-tip / 文档分析）
3. 传输协议适配（OpenAI 兼容 / Anthropic / MiniMax legacy，同步 + 流式）
4. 输出规范化与兜底（`_normalize_report`、`_mock_*`）
5. 评分规则（七维权重、硬性扣分）

建议拆分（策略 + 模板 + 服务）：

```
llm/
  client.py            # LLMClient：只负责「调用 + 重试 + 流式」
  providers/
    base.py            # Protocol: chat() / chat_stream()
    openai_compat.py
    anthropic.py
    legacy_minimax.py
  prompts/             # 模板外置（可先 Python 模板，后续接配置）
    customer.py
    report.py
    live_tip.py
  parsing.py           # extract_speaker / _json_text / _parse_live_tips
  scoring.py           # 七维权重与封顶规则（可配置化）
  mocks.py             # 模拟客户 / 模拟报告
```

协议选择现在是 `if "anthropic" in config.base_url`（`llm.py:586`），新厂商只能继续加分支——正是策略模式要解决的开闭问题。

### 3.3 依赖注入不彻底

- `LLMClient()` / `VoiceClient()` 在 handler 内直接实例化（`training.py:73,214-215` 等）
- 无法在测试里替换为 Fake，smoke_test 只能 monkeypatch 类方法
- `get_effective_llm_config()` 在 service 内部自开 `SessionLocal`

建议：FastAPI `Depends` 注入 `LLMClient` / `VoiceClient` / 各 Service；配置读取走显式 `db` 参数或 request-scoped 依赖。

### 3.4 业务规则散落且不一致

| 问题 | 位置 | 说明 |
|------|------|------|
| 权限判断两套 | `training.py:57-62` vs `151` | `_can_read` 允许 admin，`send_message`/`finish_session` 只允许 owner，admin 无法代查/代结束 |
| 七维权重写死三处 | `llm.py` prompt 文本、`_calculate_overall_score`、`_mock_report` | 改权重要改三处，极易漂移 |
| 产品卡硬编码 | `product_cards.py` 24KB 常量 | 与 `kb/` 双源；清单已列，但这是配置/数据问题，不该留在代码 |
| 型号-工艺提示词硬编码 | `services/knowledge.py:13-22` | `_MODEL_PROCESS_HINTS` 同上 |
| 评分维度白名单 | `llm.py:943-951` | 与权重 dict、prompt 文本三处重复 |
| 「建会话 + 首条客户消息」重复 | `training.py:65-78` 与 `107-140` | 应抽 `TrainingService.start_session(...)` |

### 3.5 可靠性与工程细节

1. **`GENERIC_VALUES` 含乱码**（`services/knowledge.py:10`）：`"閫氱敤"`、`"闂氨鏁?"` 是编码损坏残留，应清掉。
2. **`cryptography` 未声明依赖**：`llm_config.py` 直接 `from cryptography.fernet`，目前靠 `python-jose[cryptography]` 传递引入，属于隐式依赖，应在 `requirements.txt` 显式声明。
3. **API Key 加密密钥派生自 `jwt_secret`**（`llm_config.py:46-48`）：轮换 JWT 密钥会导致已存密文全部解密失败，应独立 `SALES_COACH_SECRET_KEY`。
4. **`_post_json` 重试无退避**（`llm.py:781-791`）：失败立即重试一次，网络抖动场景不够。
5. **`clear_my_sessions` 一键硬删全部训练**（`training.py:89-96`）：误触即清库，建议改为按 ID 批量删或加确认参数。
6. **`list_sessions` 无分页**（`training.py:86`）：`limit(100)` 截断，无法翻页。
7. **`dashboard.summary` 全量拉取到内存**（`dashboard.py:18`）：应 SQL 聚合。
8. **启动副作用**（`main.py:16-26`）：import 时 `create_all` + `seed_kb`，多 worker/测试不友好，应放 lifespan。
9. **错误信息中英混杂**：`"document not found"` vs `"训练不存在"`。
10. **JWT 12 小时无刷新机制**；CORS 域名写死 `localhost:5173`。
11. **`normalize_base_url` 白名单仅 3 个 URL**（`llm_config.py:68`），填带 `/v1` 或新厂商会被静默重置为默认值。
12. **SSE 流内嵌 200 行**（`training.py:217-269`）：建议抽 `TrainingStreamService`，路由只负责 `StreamingResponse`。

### 3.6 类型契约偏弱

- `ReportOut.scores/checklist/...` 全是 `Any`
- `_DictObj` 让 session 同时支持 dict 与 ORM，`customer_reply_stream` 里 `msg.get`/`msg.role` 双写
- 建议引入明确的 DTO（`SessionSnapshot`、`MessageSnapshot`、`ReportDTO`），SSE 与 LLM 层只认 DTO

## 四、分阶段改造建议

### 阶段 0 — 止血（改动小、收益立即）

1. 清理 `GENERIC_VALUES` 乱码
2. `requirements.txt` 补 `cryptography`
3. 独立加密密钥配置（兼容旧密文：先用新密钥，失败回退旧派生）
4. 统一 `datetime.now(timezone.utc)`，补 `updated_at`
5. 权限判断统一到 `_can_read`（admin 可读/可结束自己的代理场景）

### 阶段 1 — 数据库规范化（推荐紧接阶段 0）

1. 引入 Alembic，建立 baseline
2. 补 FK + 索引 + CHECK
3. 拆 `report_scores` / `report_todos` / `report_citations`（写时双写 JSON 保持兼容，读走子表）
4. `tags` 关联表化
5. 软删语义统一

### 阶段 2 — 后端设计模式（支撑后续开发）

1. 抽 `TrainingService` / `KnowledgeService`，路由瘦身
2. LLM 层拆 Provider（Protocol）+ Prompt 模板 + Scoring 规则
3. `Depends` 注入 Client/Service
4. SSE 流逻辑下沉 service
5. 产品卡 / 型号提示词迁出代码为配置（清单已列）

### 阶段 3 — 质量基建

1. 关键 service 单测（评分、知识检索、文档解析）
2. dashboard 聚合下推 SQL
3. 分页统一（sessions / knowledge list）
4. 配置校验与启动自检（缺依赖/缺密钥时明确报错）

## 五、不建议现在动

- 向量检索 / embedding 真实入库（先明确检索方案）
- CRM、绩效、多级组织树（清单已标暂缓）
- 全面 DTO 化全部接口（与前端契约相关，需联调）
